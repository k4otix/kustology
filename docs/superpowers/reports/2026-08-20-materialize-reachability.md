# Reachability verdict: `MaterializeExpr` cannot be produced

**Date:** 2026-08-20
**Question:** the stub sweep recorded `MaterializeExpr` as having no observed
producer, and deferred removal because *absence over one corpus is not
unreachability*. This settles it.
**Verdict:** **unreachable.** Removed in `refactor(ir)!: remove the unreachable
MaterializeExpr`.

---

## Why the earlier evidence was not enough

The sweep observed zero occurrences across the 33-query corpus and a handful of
hand-written shapes. That is consistent with unreachability and also consistent
with "we did not think of the right query". Deleting a public exported model on
that basis would have been a guess. Three stronger methods were run instead, and
they agree.

## 1. Grammar — where the parser will accept the keyword

Microsoft's own completion engine (`KustoCodeService.GetCompletionItems`) was
swept across **every character offset** of 20 template queries covering
`where` / `extend` / `project` / `summarize` / `join` / `union` / `mv-apply` /
`partition` / `fork` / `facet` / `evaluate` / `scan` / `make-series` / `print` /
`search` / `find` / `datatable` / `toscalar` and function bodies, filtering for
the exact token `materialize`.

Positions where the grammar offers it:

```
'let A ='     'let A = '     'let A = T'     'let f ='     'let f = '
```

Nothing else. Notably **not** inside a `let f = (x:long) { … }` body, and **not**
after `T | join (`.

## 2. Parse trees — where the node actually lands

1,808 mutations were generated by inserting `materialize(T|count)`,
`materialize(T)`, `(materialize(T))` and `materialize (T)` at every token
boundary of 14 template queries, each parsed with `KustoCode.Parse` so that
**error-recovery trees are included**, not only clean parses. The parent kind of
every `MaterializeExpression` node was tallied:

```
mutations tried: 1808
MaterializeExpression parent kinds: {'LetStatement': 18}
non-LetStatement parents: 0
```

Zero, even in malformed trees. Where the keyword is misplaced the parser emits
*"Missing expression: If the keyword 'materialize' is intended to be part of an
expression it needs to be bracketted as ['materialize']"* and drops the node
rather than building one.

Confirmed independently while implementing (`.Count`, not truthiness — see the
footnote):

| Query | Diagnostics |
|---|---|
| `let A = materialize(S \| count); A \| count` | **0 — clean** |
| `T \| where materialize(S \| count) > 1` | 2 |
| `let A = (materialize(S \| count)); A \| count` | 3 |
| `materialize(S \| count) \| count` | 1 |

The third line matters on its own: `materialize` cannot hide inside a
`ParenthesizedExpression` that `_visit_let_statement`'s unwrap loop would strip.

## 3. Instrumented builder — what `_visit_expr` actually receives

`IRBuilder._visit_expr` was wrapped to log the incoming node class, then the
corpus plus the mutation set were built. Two independent runs:

```
run A   978 queries    MaterializeExpression -> _visit_expr:  0
                       ToScalarExpression (control):          4
                       PipeExpression     (control):         57

run B   113 queries    MaterializeExpression -> _visit_expr:  0
        3,237 calls    ToScalarExpression (control):          7
                       PipeExpression     (control):          1
```

The sibling branches fire. This one never does.

## Why the single reachable path is closed

`materialize` reaches the builder only as a `let` right-hand side, and
`_TABULAR_LET_RHS_KINDS` (`builder.py`) lists `MaterializeExpression`, so
`_visit_let_statement` routes it to `_visit_pipeline` — which builds a **nested
`Pipeline`**, the shape the IR actually models. `_visit_expr`'s branch sat behind
that guard from the beginning.

Both branches shipped in the same commit (`8ad2b28`, the v0.1.0 release), so this
was never a regression: it is speculative surface that was written alongside the
handler that superseded it, and never removed.

## What removal did and did not touch

Removed: the class, its `AnyExpr` union entry and `model_rebuild` tuple, the
`SubqueryExpr` docstring reference, the `builder.py` import and dead
`_visit_expr` branch, the `query.py` forward-ref import (an `ImportError` if
left), the `_normalize.py` import and `canonical()` case, and the
`ir/__init__.py` export and `__all__` entry.

**Deliberately kept:** `"MaterializeExpression"` in `HANDLED_EXPR_KINDS`. The
.NET kind genuinely *is* modelled — by `_visit_pipeline`. Dropping it would make
`scripts/audit_syntax_kinds.py --check` exit 1 by reclassifying a fully-handled
shape as unhandled. Verified: the audit passes with no baseline update.

Also kept: the `transforms.py` and `binder.py` comments about `materialize`,
which describe the nested-`Pipeline` source form and remain accurate.

## Safety

Because no `MaterializeExpr` was ever produced, **no stored IR JSON can contain
one**, so the removal breaks no deserialization despite `extra="forbid"`. This is
unusual for a breaking model change and is the reason it could ship without a
migration path.

## Regression guard

`test_materialize_appears_only_on_a_let_right_hand_side` pins the grammar fact
rather than the IR consequence, so it survives the class being gone and turns red
if a DLL refresh ever widens the grammar — at which point the shape needs
modelling again, deliberately.

---

**Footnote — a pythonnet trap found while reproducing this.** An empty .NET
`IReadOnlyList` is **truthy** in Python, so `if not code.GetSyntaxDiagnostics():`
never fires and every query looks like a parse error. Use `.Count`. The library
itself was checked and does not contain this pattern.
